分工：人事拿「done 课次 × 合同课时单价」算出月度汇总 → 提交 zhops/approvals → 财务核对批准 / 驳回 → 人事记发放。

⑩ 课次完成怎么同步给人事 已定已落实
每标一节 done 就写一条
做法：主端「推进一课」、教师端「这节课已上完」→ 立刻 PATCH zhops/done_<课次ID>，只写这一节。
为什么不沿用整份推送：整份推送是全手动的（2026-10-17 定，系统还在搭建），一天 done 十节课也不会自动推。人事那边看到的是几天前的数据。
两条路不打架：整份推 zhops/master（备份用）；增量写 zhops/done_*（人事用）。路径不同，互不覆盖。
人事端合并规则：拉 master 之后再拉一遍 done_*，取那条为准。只认 done / plan / cancel 三种，别的值一律忽略；不凭空造课（云端有、master 没有的课次直接跳过）。
能退（2026-10-31 补）：主端课次记录可以逐节改状态。done → plan 就是撤回 —— 写同一条 done_* 覆盖成 plan，人事重算时那节就扣掉。cancel 同理。

库归属 · 怎么拆
市场的数据不是「一个系统一个风险级」，是三类数据三个去处：
① 渠道账号密码（FB / Zalo / 微信后台）→ 不进任何数据库，放密码管理器。系统里只存账号名 + 「密码在哪个管理器」的备注。
② 广告投放花费 → 进财务库。它本来就是支出科目，归财务天经地义。
③ 素材 / 活动 / 渠道发布计划 / 销售赛道 → 进业务库。这些是业务级，泄露损失跟排课同级。
拆完的结果：业务部剩下的全部是业务级数据 → 跟排课放一起，不需要第三个库。
为什么密码不能进库
你的 Firestore 现在是无认证可读（我实测过 200）。把 Facebook / Zalo 后台密码写进去，等于贴在公网上。
就算以后加了认证，密码也不该躺在一个前端页面能读到的地方 —— 一旦 XSS 或 key 泄露，全丢。
密码管理器（1Password / Bitwarden）就是干这个的，别再自己造。
连带好处：密码一搬走，市场的风险等级立刻降一档，分库问题自动消失。
一个要留意的点
客户线索名单（姓名 + 电话）也归市场，会进业务库。它算个人信息，越南有专门法规管。
具体条款我没核，等真要建这块时我查一遍再说。现在只需记住：以后加认证时，这块名单要单独设规则，不能跟排课数据同权限。
